## 1. Purpose & scope

Single contract between the citizen website and the FastAPI core. Both sides build against this only.

| Endpoint | Purpose |
|---|---|
| `POST /api/v1/message` | One citizen turn (text, voice, and/or location) and the bot's reply |
| `GET /api/v1/status/{complaint_id}` | Status lookup by complaint ID |
| `GET /health` | Liveness and pre-demo warm-up |

The dashboard is **not** a client: it reads and writes the database directly and never calls the core.

## 2. Principles

1. **The website holds no business logic.** It sends input and renders the response.
2. **The backend never trusts the LLM.** Every value returned has been validated against the service spec.
3. **Anonymous by default.** `session_id` is the only identity.
4. **Privacy on lookup.** The status endpoint never returns transcript, audio, location, contact details, or collected fields.
5. **Service fields are data, not schema.** Keys inside `summary` come from `specs/*.yaml`, so a new service needs no contract change.
6. **Tolerant clients.** Clients ignore unknown response fields and treat an unknown `action` as `error`.

## 3. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1` for business endpoints; `/health` has no prefix |
| Request encoding | `POST /message` is `multipart/form-data`; responses are `application/json; charset=utf-8` |
| Text | UTF-8. Devanagari and Latin (Hinglish) are both valid |
| IDs | `session_id`, `message_id`: UUID v4, lowercase, hyphenated. `complaint_id`: `SMD-` + zero-padded number, at least 4 digits (e.g. `SMD-0007`) |
| Timestamps | ISO 8601, UTC, e.g. `2026-09-27T10:30:00Z` |
| Coordinates | WGS84 decimal degrees |
| Nulls | Fields are always present; absent values are `null`, never omitted |
| CORS | Only origins listed in the `ALLOWED_ORIGINS` env var |
| Auth | None. `session_id` is an unguessable bearer value |

## 4. `POST /api/v1/message`

### 4.1 Input (`multipart/form-data`)

| Field | Type | Required | Rule |
|---|---|---|---|
| `session_id` | UUID v4 | ✅ | Generated by the website and kept in the browser. A new ID makes the server create a session |
| `message_id` | UUID v4 | ✅ | Unique per message; used for de-duplication |
| `text` | string | one of | 1–1000 chars, trimmed |
| `audio` | file | one of | `webm` / `ogg` / `mp4` / `wav`; ≤ 60 s; ≤ 2 MB `[limits to confirm]` |
| `lat`, `lng` | float | one of / ❌ | Both or neither; `lat` −90..90, `lng` −180..180 |

- At least one of `text`, `audio`, or (`lat` + `lng`) must be present.
- `text` and `audio` together are rejected (`INVALID_INPUT`). **One modality per turn.**
- `lat`/`lng` may accompany `text` or `audio`, or be sent alone (the location button).
- The messages `cancel` and `restart` (case-insensitive, trimmed) are commands, recognised by the backend. They are not separate fields. A fixed set of Hindi/Hinglish aliases (e.g. `रद्द करो`, `शुरू से`) is recognised too, and so is a spoken command: the audio transcript is matched the same way (S20 §5). Whole-utterance match only.

**Audio:** the accepted types are what `MediaRecorder` produces (Chrome/Firefox `webm`/`ogg`, Safari `mp4`). The backend converts to 16 kHz mono WAV with FFmpeg before ASR. The original audio and the transcript are preserved server-side (PROJECT.md §7, §13).

### 4.2 Output — `200` JSON

| Field | Type | Rule |
|---|---|---|
| `session_id`, `message_id` | string | Echo of input |
| `action` | enum | `ask` · `confirm` · `submitted` · `cancelled` · `out_of_scope` · `error` |
| `reply_text` | string | In the citizen's language; always present, never empty |
| `ask_for` | string \| null | The field being asked for when `action = ask` (e.g. `"location"`); lets the UI show a location button |
| `transcript` | string \| null | Only when the input was audio |
| `summary` | object \| null | Only when `action = confirm`: collected fields for the citizen to check |
| `ticket` | object \| null | Only when `action = submitted`. See 4.4 |
| `duplicate` | bool | `true` when this `message_id` was already processed |

### 4.3 `action` values

| `action` | Meaning | Client behaviour |
|---|---|---|
| `ask` | A required field is missing (also the reply to `restart`) | Show `reply_text`; if `ask_for = "location"` offer the location button |
| `confirm` | All fields collected | Show `summary`; expect a yes, a correction, `cancel`, or `restart` |
| `submitted` | Ticket saved and routed | Show `ticket`; the conversation is finished |
| `cancelled` | User sent `cancel` | Show `reply_text`; session state cleared |
| `out_of_scope` | Request is not a supported service | Show `reply_text`; session continues; no service is invented |
| `error` | Input was not usable but the system is healthy (empty transcript, unintelligible audio, LLM output failed validation) | Show `reply_text`; let the user retry or type instead |

`error` is a **recoverable, HTTP 200** outcome. Provider outages use HTTP `503` (see §7).

### 4.4 `ticket` object

| Field | Type | Rule |
|---|---|---|
| `complaint_id` | string | Matches `SMD-\d{4,}` |
| `department` | string | Department name from the service spec |
| `office` | object | `name` = `offices.office_name` (S02). `{ "name": string, "level": "ward" \| "zone" \| "municipal_corp" \| "gram_panchayat" \| "block" \| "district" }` |
| `status` | enum | `new`, or `needs_review` when routed to the district fallback (PROJECT.md §7 step 7) |

### 4.5 Examples


```json
  "transcript": null,
  "summary": null,
```

Ticket submitted (scenario 7):

```json

  "message_id": "9c2e4d70-1b3a-4f6e-a8d5-7e0b2c1f3a44",
```

## 5. `GET /api/v1/status/{complaint_id}`

Response `200` JSON — exactly these four fields:

| Field | Type | Rule |
|---|---|---|
| `complaint_id` | string | Echo |
| `status` | enum | `new` · `in_progress` · `resolved` · `needs_review` |
| `department` | string | Department name |
| `updated_at` | string | ISO 8601 |

```json
{ "complaint_id": "SMD-0042", "status": "in_progress", "department": "Jal Vibhag", "updated_at": "2026-09-29T09:15:00Z" }
```

Never returns transcript, audio, location, contact details, or collected fields.

Errors: `400 INVALID_COMPLAINT_ID` for a malformed ID; `404 COMPLAINT_NOT_FOUND` for a valid ID with no ticket.

## 6. `GET /health`

```json
{ "status": "ok" }
```

No auth. No external calls: it must not touch the database, ASR, or LLM.

## 7. Errors

Every non-2xx response has the same JSON body:

```json
{
  "error_code": "INVALID_INPUT",
  "message": "Provide text or audio, not both.",
  "reply_text": "कृपया एक बार में केवल टेक्स्ट या आवाज़ भेजें।",
  "request_id": "e5a1c0d2"
}
```

| HTTP | `error_code` | When |
|---|---|---|
| 400 | `INVALID_INPUT` | Neither/both text & audio; bad UUID; `lat` without `lng`; text outside 1–1000 chars |
| 400 | `INVALID_COMPLAINT_ID` | Status ID fails the format |
| 404 | `COMPLAINT_NOT_FOUND` | Valid format, no ticket |
| 413 | `AUDIO_TOO_LARGE` | Over the size or duration limit |
| 415 | `UNSUPPORTED_AUDIO` | Audio type not in §4.1 |
| 503 | `SERVICE_UNAVAILABLE` | ASR or LLM primary **and** fallback failed |
| 500 | `INTERNAL_ERROR` | Anything else |

- `message` is for developers and logs. `reply_text` is citizen-safe and can be shown as-is.
- `request_id` is generated per request and logged, so a failure during the demo can be traced.
- Validation errors use `400`, not FastAPI's default `422`. The backend must override the default handler.

## 8. Sessions & idempotency

- The website generates `session_id` (UUID v4, e.g. `crypto.randomUUID()`) and keeps it in the browser. An unknown ID makes the server create a session.
- Sessions are isolated: state and messages never cross sessions (scenario 10).
- Inactivity timeout: **30 minutes** (PROJECT.md §6). A request with an expired `session_id` starts a fresh session under the same ID and is still processed, so a voice note is never dropped (D-A2).
- After `submitted` or `cancelled`, conversation state is cleared and the same `session_id` may be reused.
- `(session_id, message_id)` is unique. A repeated `message_id` returns the **stored response unchanged except `duplicate = true`**. It does not re-run ASR, the LLM, or ticket creation. This guarantees one ticket per confirmed complaint despite double-taps and network retries.

## 9. Rules

1. `complaint_id` format: `SMD-` + zero-padded number (≥ 4 digits), e.g. `SMD-0007`.
2. Same `message_id` → stored response, `duplicate = true`, no reprocessing.
3. `reply_text` is always citizen-safe: no stack traces, keys, or internal names.
4. CORS allows only origins listed in the `ALLOWED_ORIGINS` env var.
5. `GET /health` → `{"status":"ok"}`; no auth; no external calls.
6. The T08 mock must return schema-valid responses for **every** `action` value.
7. **Changing the contract:** either of us can change it at any time. Update `schemas.py` and this spec together and tell the other, so the mock and the contract tests stay in sync. Prefer additive changes (a new optional field) so the other side isn't broken mid-way.

## 10. Acceptance

### 10.1 Contract tests

The mock and the real API must pass the same tests.

- [ ] Text message → `200` with a valid `action` and non-empty `reply_text`
- [ ] Audio message → `200` with `transcript`
- [ ] Both text and audio → `400 INVALID_INPUT`
- [ ] Repeated `message_id` → identical body except `duplicate = true`
- [ ] `action = submitted` → `ticket.complaint_id` matches `SMD-\d{4,}`
- [ ] Status of an existing ID → `200` with only the 4 allowed fields
- [ ] `SMD-ABC` → `400`; `SMD-9999` (missing) → `404`
- [ ] Request from a non-allowed origin → blocked by CORS
- [ ] Mock returns a valid response for each of the 6 `action` values

### 10.2 The 10 MVP scenarios (PROJECT.md §17)

| # | Scenario | Request | Pass when the response shows |
|---|---|---|---|
| 1 | Hindi voice: "3 दिन से पानी नहीं आ रहा" | `audio` | `transcript` set, `action = ask`, `ask_for = "location"` |
| 2 | Hinglish text | `text` | Same as 1 |
| 3 | All details in one message | `text` | `action = confirm`, `summary` populated |
| 4 | Correct a field at confirmation | `text` | `action = confirm` again with the corrected value in `summary` |
| 5 | `cancel` | `text = "cancel"` | `action = cancelled` |
| 6 | Unrelated request | `text` | `action = out_of_scope` |
| 7 | GPS in pilot ward | `lat` + `lng` | `action = submitted`, `ticket.office.level = "ward"` |
| 8 | Unknown location | `text` | `ticket.office.level = "district"`, `ticket.status = "needs_review"` |
| 9 | Officer sets "In progress" | `GET /status/{id}` | `status = "in_progress"` |
| 10 | Two browsers at once | Two clients | Different `session_id`s; `summary` never shared |

## 11. Decisions

| # | Decision | Reason |
|---|---|---|
| D-A1 | Multipart only for `POST /message`; one modality (`text` or `audio`) per turn | One code path; no ambiguity about which input to trust |
| D-A2 | Expired session → fresh session, message still processed | A citizen's voice note is never thrown away |
| D-A3 | `cancel` / `restart` are commands; `restart` replies with `ask`. Amended by S20 (T28): aliases and spoken (transcribed) commands count too | Small request; fewer `action` values to mock and test. A voice-first citizen must be able to cancel by voice |
| D-A4 | `ask_for` tells the UI what is being asked | The website needs to show a location button without holding logic |
| D-A5 | `ticket.office` is `{name, level}`, not a string | Scenarios 7 and 8 can be checked by `level` (ward vs district) |
| D-A6 | `error` is a recoverable HTTP 200; outages are `503` | Bad audio is normal for a voice product, not a server fault |
| D-A7 | Error body carries `reply_text` and `request_id` | The website can show it unchanged; failures can be traced |
| D-A8 | Location may be sent alone | The location button needs no fake text message |
| D-A9 | Audio accepts `mp4` as well as `webm`/`ogg`/`wav` | Safari (iPhone) records `mp4`; the pilot users are on mobile |

## Appendix A — `schemas.py` model sketch

Illustrative shape for T02. `MessageRequest` documents the form fields; `audio` is an `UploadFile` at the route level.

```python
from datetime import datetime
from enum import StrEnum
from typing import Any

from pydantic import UUID4, BaseModel, Field

COMPLAINT_ID_PATTERN = r"^SMD-\d{4,}$"


class ComplaintStatus(StrEnum):
    NEW = "new"
    IN_PROGRESS = "in_progress"
    RESOLVED = "resolved"
    NEEDS_REVIEW = "needs_review"


class Action(StrEnum):
    ASK = "ask"
    CONFIRM = "confirm"
    SUBMITTED = "submitted"
    CANCELLED = "cancelled"
    OUT_OF_SCOPE = "out_of_scope"
    ERROR = "error"


class OfficeLevel(StrEnum):
    WARD = "ward"
    ZONE = "zone"
    MUNICIPAL_CORP = "municipal_corp"
    GRAM_PANCHAYAT = "gram_panchayat"
    BLOCK = "block"
    DISTRICT = "district"


class ErrorCode(StrEnum):
    INVALID_INPUT = "INVALID_INPUT"
    INVALID_COMPLAINT_ID = "INVALID_COMPLAINT_ID"
    COMPLAINT_NOT_FOUND = "COMPLAINT_NOT_FOUND"
    AUDIO_TOO_LARGE = "AUDIO_TOO_LARGE"
    UNSUPPORTED_AUDIO = "UNSUPPORTED_AUDIO"
    SERVICE_UNAVAILABLE = "SERVICE_UNAVAILABLE"
    INTERNAL_ERROR = "INTERNAL_ERROR"


class MessageRequest(BaseModel):
    session_id: UUID4
    message_id: UUID4
    text: str | None = Field(None, min_length=1, max_length=1000)
    lat: float | None = Field(None, ge=-90, le=90)
    lng: float | None = Field(None, ge=-180, le=180)
    # Route-level checks: one of text/audio/(lat+lng); not text+audio; lat and lng together.


class Office(BaseModel):
    name: str
    level: OfficeLevel


class Ticket(BaseModel):
    complaint_id: str = Field(pattern=COMPLAINT_ID_PATTERN)
    department: str
    office: Office
    status: ComplaintStatus


class MessageResponse(BaseModel):
    session_id: UUID4
    message_id: UUID4
    action: Action
    ask_for: str | None
    reply_text: str = Field(min_length=1)
    transcript: str | None
    summary: dict[str, Any] | None
    ticket: Ticket | None
    duplicate: bool


class StatusResponse(BaseModel):
    complaint_id: str = Field(pattern=COMPLAINT_ID_PATTERN)
    status: ComplaintStatus
    department: str
    updated_at: datetime


class HealthResponse(BaseModel):
    status: str = "ok"


class ErrorResponse(BaseModel):
    error_code: ErrorCode
    message: str
    reply_text: str
    request_id: str
```
