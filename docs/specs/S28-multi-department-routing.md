## 1. Goal (Lead, 29 Sep)
"Understand the complaint well enough to route it." A citizen says any complaint in their own words; the system picks the
right **department**, finds the right **office**, creates the ticket there, and an officer of that department can see it.
Perfect dialect transcription is explicitly not a goal (S21/S-eval: the bot already understands Bundeli/Malvi well enough).
Today only `water_supply` exists, so the demo routes between 5 wards of one department, not between departments.

## 2. What already generalises (verified in code, 29 Sep)
- `Turn Engine` already receives *all* loaded specs and returns a `service_id` (S05); the validator, `create_ticket` and the
  jurisdiction resolver are all keyed by `spec.department` (S07, S10, S09). A new department is mostly **data**: a spec file plus
  office rows.
- `offices` already supports many departments (`UNIQUE (department, level, code)`, one active district office per department).
- The dashboard already filters by department and office; the review queue and reassign already exist. Only its issue labels are
  water-specific (`labels.py`).

## 3. What is genuinely missing
1. **Unsure handling.** Today `service_id = null` means "decline" (`out_of_scope`). There is no "which department?" question and no
   "is this an X problem, right?" reconfirmation, and no general triage bucket for a complaint that fits no department.
2. **Per-department data:** spec files, DEMO offices, labels.
3. **Delivery to the department.** A ticket lands in the DB and on the dashboard. Nothing is pushed to an officer.

## 4. Design
### 4.1 Departments for the demo (all office data DEMO, labelled, like the ward rows; nothing invented as fact)
| Service id | Department (DEMO) | Issue types (curated, hi + en) |
|---|---|---|
| `water_supply` (exists) | Jal Vibhag | no supply, low pressure, dirty water, leakage, other |
| `electricity` | Electricity Department | no power, low/high voltage, pole or wire down, bill/meter, other |
| `roads` | Roads / PWD | pothole, broken road, other |
| `sanitation` | Municipal sanitation | garbage not collected, drain blocked, dirty area, other |
| `general` | General triage | (only a free description + location) catch-all, always `needs_review` |
Every non-water spec is deliberately minimal: `issue_type` + `location` (+ optional duration). Route the complaint, do not try to
resolve it (Lead's principle). Questions are **written by us in the spec, not generated by the LLM** (D-S28-2).

### 4.2 Offices (DEMO)
Per new department: one active `district` row (mandatory for the fallback) and, where useful for the demo, ward rows reusing the
5 pilot ward names with department-specific office names. All marked DEMO in `office_name`/comments. Centroids stay `NULL` (S09).

### 4.3a First decide the kind of message (added 29 Sep, Lead)
Before choosing a department the Turn Engine labels the message with one **intent**. Three fixed outcomes, all answered by
backend-written text (never LLM-written, D-S28-2):
| Intent | Example | Reply |
|---|---|---|
| `complaint` | "बिजली नहीं आ रही" | goes on to 4.3 (department, questions, ticket) |
| `information` | "आय प्रमाण पत्र कैसे बनेगा?", any document or scheme question | fixed message + an official link, **no invented facts** (4.6) |
| `out_of_context` | jokes, chit-chat, general knowledge, anything that is neither a complaint nor a document question | fixed "I am unable to reply to this kind of question" message (4.6) |
The `general` triage bucket (4.3) is only for a real **complaint** that fits no listed department. It is not for chit-chat.

### 4.3 Classification and asking
The Turn Engine output gains `confidence` (0-1) and `candidates` (service ids). The **backend** decides, from fixed thresholds,
and writes the question itself from spec labels (no LLM-written text):
| LLM result | Backend action |
|---|---|
| a service, confidence >= 0.8 | continue with that department's questions |
| a service, 0.5 <= confidence < 0.8 | **reconfirm**: "क्या यह <department label> की समस्या है?" (yes -> continue, no -> ask which) |
| no service but 2+ candidates | **clarify**: "क्या यह <A> की समस्या है या <B> की?" |
| no candidates / nothing fits | **general** triage service (collect description + location), `needs_review`, never a bare decline |
| a safety-critical complaint (fire, medical, crime, cyber fraud) | do not queue silently: show emergency guidance. **OPEN Q4** |
LLM-reported confidence is uncalibrated; thresholds are tuned on the classification test set (5.), not assumed.
The yes/no answer to a reconfirm/clarify is understood from the conversation history (S05 already passes the last turns) plus a
prompt rule; the validator only ever accepts a service id that exists in the loaded specs (S05/S07 unchanged guarantee).

### 4.6 The two fixed replies (spoken by the Sarvam voice like every bot reply; both use the existing `out_of_scope` action, so no contract or frontend-logic change)
- **Information / document request (Lead's design, 29 Sep: the LLM proposes the link, `.gov.in` only, with a disclaimer).**
  Three parts, in this order, all but the link being fixed backend text:
  1. Message (hi, proposed): `मेरे पास अभी इसकी कोई आधिकारिक जानकारी नहीं है। जब मेरे डेवलपर को सरकार के साथ काम करने का मौका मिलेगा, तब मैं आपकी मदद करने की पूरी कोशिश करूँगा।`
  2. Link line: `आप यहाँ देख सकते हैं: <link>`, only when a link passed validation (below); otherwise this line is simply omitted.
  3. Disclaimer, **always** appended, fixed text: `ध्यान दें: मैं कोई आधिकारिक स्रोत नहीं हूँ, इसलिए यह जानकारी सही न भी हो सकती है। कृपया आधिकारिक वेबसाइट पर जाँच लें।`
  The voice note speaks 1 and 3; the link is shown, not read aloud. URLs in bot replies become real anchors in `app.js`/`widget.js`
  (built with the DOM, `rel="noopener noreferrer"`, `target="_blank"`, never innerHTML).
  **Link validation (deterministic, in the backend, LLM output is untrusted):** the Turn Engine returns an optional `info_url`. It is kept
  only if ALL hold: scheme is `https`; no userinfo (`@`), no port, not an IP address; the host, lower-cased, ends with `.gov.in` on a label
  boundary (`x.gov.in` yes; `gov.in.evil.com`, `evilgov.in`, `x.nic.in` no); then the path, query and fragment are **discarded** (homepage
  only: an LLM that invents a deep path would otherwise produce a 404); and the host **resolves in DNS** within 2 s (a hallucinated
  subdomain is dropped). Anything failing = no link, message + disclaimer only. Never a failure to the citizen.
  **What this does and does not protect:** it removes phishing and lookalike domains (only government bodies can hold `.gov.in`) and dead
  or invented hosts. It **cannot** tell whether a real `.gov.in` site is the *right* site for the question (the LLM may pick a real but wrong
  department's site); that is exactly what the disclaimer is for. Not a guarantee, a risk reduction, stated honestly.
- **Out of context.** Hindi, proposed: `माफ़ कीजिए, मैं इस तरह के सवाल का जवाब नहीं दे सकता। अगर आपकी कोई समस्या या शिकायत है तो मुझे बताइए।` (the last sentence
  is an optional nudge back to a complaint; the Lead's wording was only "I am unable to reply to this kind of question").
- Which official site to link is **OPEN Q6** (I will not guess a URL). "ज़रूर मदद करूँगा" is a promise made for the developer: **OPEN Q7**.

### 4.4 Delivery to the department
- **Phase A (in scope):** dashboard gets a per-department view: a department filter that is already there, a per-department
  count of `new` tickets on top, and the general triage queue in the review tab. Officers correct a wrong department with the
  existing reassign action; corrections are logged in `routing_corrections` (future training labels).
- **Phase B (not in scope, needs a provider and real addresses):** push to the office by email/WhatsApp. Listed on the roadmap.

### 4.5 Contract
Additive only: `ask_for` gains the value `service` for the clarify/reconfirm question (S01 §4.3). The frontend needs no change
(it only special-cases `location`). No new endpoint, no new DB column, no schema migration (offices are rows).

## 5. Measurement (the pitch number)
A classification test set, built from the synthetic Bundeli/Malvi files (deduplicated, ~334 unique) plus hand-written Hinglish
and Hindi cases, each labelled with the expected department. Report honestly, per department: **department accuracy**, **office
accuracy**, share sent to `general`, share that triggered a question, and false routes. Same discipline as T13 (runs kept, no
tuning to the result, synthetic caveat stated).

## 6. Effort, risk
- **Effort:** ~4-5 h with the minimal specs (spec files, seed SQL, prompt, validator branch, dashboard labels, tests, test set + runs).
- **Risk:** touches the core turn path the day before the freeze; more prompt tokens on a rate-limited quota (the S26 chain helps);
  DoD scenario 6 ("unrelated request -> polite decline") changes meaning: it becomes "goes to `general` triage". PROJECT.md scope
  ("1 service, other services not now"), README and the pitch must be updated together.
- **Fallback plan:** every step is additive and behind the spec directory: removing the new spec files returns the exact current
  single-service behaviour.

## BUILD LOG (29 Sep 2026)

Triage; `database/seed_departments.sql`, applied through the service API because the direct DB host is unreachable from the dev
machine); Turn Engine output `intent / confidence / candidates / urgent / info_url` and a compact prompt; `app/info_reply.py`
(fixed replies + strict `.gov.in` link validation); validator decisions (route, reconfirm, clarify, general, sticky active service,
department switch that drops another department's enum values); dashboard cross-department reassign (also moves
`tickets.department`), per-department open counts, labels; chat links (https `*.gov.in` only, URL line never spoken).
**Tests:** backend 356 passed (60 new: `test_routing_decisions`, `test_info_reply`), dashboard 28 passed, ruff clean.
**Live, end to end (real Groq/Supabase), `demo_multi` script, 13 checks:** each of water / electricity / roads / sanitation created a
ticket at that department's own ward office (e.g. `SMD-0033` -> `Ward मिसरोद Bijli Office (DEMO)`); teacher absence -> General Triage
district desk with `needs_review`; an income-certificate question -> message + `https://www.incometax.gov.in` (a real, resolving
`.gov.in` homepage the LLM picked, kept by the validator) + disclaimer; chit-chat -> fixed "unable to reply"; fire -> neutral
emergency line, no number; the status page shows the ticket's department. First run 13/13, final run 12/13: the one miss (a side
question in the middle of a complaint) passed when replayed twice, so it was a transient model-quota failure, not a logic bug.
**Routing accuracy (`tests/prompt/run_routing_eval.py`, 60 messages: 26 hand-written + 34 from the SYNTHETIC Bundeli/Malvi files, one
run each, files in `submission/routing-eval-results-run{1-first,2-prompt-diet}.json`):**
run 1 hand 25/26 (96%), synthetic 30/34 (88%); run 2 (after cutting the prompt 23%) hand 25/26 (96%), synthetic 29/34 (85%). All
five recurring "misses" are debatable, not clear errors: a vague "बहुत परेशानी है यहाँ" declined as chit-chat; three "name is wrong in my
voter card / birth certificate" sentences labelled information in the synthetic set but sent to general (they are complaints about a
document, arguably correct); one water-pump-motor sentence sent to electricity; one Bundeli garbage sentence sent to general in run 1
only. So roughly 90% exact, ~95% if the debatable labels are read the other way. **Caveats:** synthetic data written by an LLM, not
checked by native speakers; small sample; most calls in run 2 were answered by the fallback models because the primary model's quota
was spent, which is itself a useful result (routing holds on `qwen3.8-27b`).
**T13 (water-only, run 7, `...run7-after-s28.json`): 9/15**, not comparable to runs 5-6: 3 of 15 were 503 (quota, see below) and the rest
changed on purpose: the drainage sentence now routes to sanitation (correct now that it exists), the pipe-broke-onto-the-road sentence
asks which department. T13 was written for a one-service bot and should be re-baselined.
**Capacity finding (Groq free tier, measured from response headers):** each model allows **8,000 tokens per minute** and 1,000
requests per day. One turn costs about 1,800 prompt tokens plus the reply, so a single model serves roughly 3-4 turns a minute, and
heavy testing exhausted `gpt-oss-120b` for the day (`429`, `retry-after` ~54 s). The S26 chain absorbs it (three Groq models), but
demo traffic should be paced and everything warmed up first. The prompt was trimmed 23% (6,803 -> 5,249 characters) to help.
**Not verified:** a real spoken clarify/reconfirm answer; the department reconfirm on a genuinely 0.5-0.8 confidence message (the
live runs never produced one, only unit tests cover it); the dashboard reassign across departments in a browser (unit tested and the
app runs against live data, the click itself not exercised); the link on a phone; the info reply's voice note in a real browser session.
